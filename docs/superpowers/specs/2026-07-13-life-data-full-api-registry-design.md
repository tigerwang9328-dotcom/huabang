# LifeData 全量 API 注册表采集设计

## 目标与范围

本次只完善第一阶段的数据采集底座，不制作投流分析看板，不自动执行投放。页面仅用于首次发现真实业务请求；模板登记完成后，任意一个已登录的 LifeData 标签页作为运行载体，由油猴直接调用业务 API。用户不需要停留在视频、经营或广告分析页面。

采集范围包括视频分析、经营与实际核销、广告消耗、广告成交、素材排行、人群购买分布、年龄性别、地域、门店排行及页面后续出现的同类业务模块。Cookie、Authorization 和会话头只在浏览器内使用，永不上传服务器。

## 模板注册表

每个成功请求保存为一个模板，模板身份由以下字段共同确定：

- LifeData API endpoint；
- 业务 `path`；
- Dito 更新节点或模块集合；
- 去除日期、分页游标等易变值后的请求结构指纹。

同一模块因首次渲染、局部刷新或重复标签触发的相同请求只保留一个有效模板。模板记录首次发现、最后学习、最后成功、连续失败次数、最近响应摘要和所属采集组。响应必须为成功业务 JSON；解释文本、空响应及无业务字段的模板不参与定时重放。

预置采集组：

- `video`：视频列表及视频指标，每 5 分钟；
- `business`：成交、实际核销、退款、券数、用户数和趋势，每 30 分钟；
- `advertising`：消耗、广告成交、素材排行、人群、年龄性别、地域和趋势，每 30 分钟；
- `other`：门店排行及后续学习到的白名单业务模块，每 30 分钟。

## API 重放

主标签按注册表调度模板，通过页面原生 `fetch` 携带当前登录态直接请求 `/api/dito/query` 或 `/api/lowcode_api/query`。重放前自动刷新统计日期，并保留账号、模块及筛选条件。视频列表继续按总数和 `offset/limit` 拉完全部分页；其他分页模块在发现总数或游标时使用同一分页策略。

一次调度只允许一个采集动作执行。同一模板在上次动作尚未结束时不重复启动。多标签页仍采用主标签租约，避免重复调用；主标签关闭后由其他 LifeData 标签自动接管。

## 数据上传与完整性

每个 API 响应仍通过现有只写接口上传 AI 中台。事件 ID 保证重试幂等，失败数据进入本地队列并按退避时间补传。后端保留原始业务 JSON；标准化广告与经营数据将在后续看板阶段落入专用快照表。

每轮采集生成模块结果：成功、空数据、登录失效、结构变化、请求失败或上传排队。完整性规则至少检查：

- 视频组 10 分钟内有一次完整成功；
- 经营、广告组 60 分钟内有一次有效成功；
- 视频分页数量与接口总数一致；
- 广告组包含总消耗及至少一个人群、地域或素材维度；
- 经营组包含实际核销金额；
- 当前主体与配置主体一致。

连续超过完整性窗口时，采集器显示缺失模块，并向 AI 中台生成一条去重的采集异常待办；恢复后更新状态，不重复创建待办。

## 浮层反馈

浮层新增：已登记模板数、视频/经营/广告/其他组状态、最近全量成功时间、失败模块和下次运行时间。“立即采集”改为触发全部采集组，执行中禁用并显示“采集中…”，结束后显示成功模块数、失败模块数和上传队列数。

## 安全与失效处理

不向后端传 Cookie、Authorization、会话头或浏览器存储。登录过期时停止重放业务模板并提示重新登录；API 返回结构变化时保留旧模板但标记失效，等待页面真实成功请求重新学习覆盖。浏览器关闭后不采集，重新打开任意 LifeData 标签后自动恢复调度和离线队列。

## 测试与验收

油猴测试覆盖模板指纹去重、有效业务模板筛选、分组调度、日期刷新、分页、主标签接管、立即全量采集、失败隔离和队列补传。后端测试覆盖模块状态、异常待办幂等及恢复。

线上验收标准：离开广告分析页后仍能在任意 LifeData 页面定时调用广告模板；连续两轮采集均取得总消耗、素材、人群和地域数据；视频分页完整；经营页实际核销有效；重复响应不重复生成数据或异常待办；上传内容不含任何登录凭证。
